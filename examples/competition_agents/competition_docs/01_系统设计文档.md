# 系统设计文档

## 1. 文档目标

本文档说明本项目如何围绕赛题要求，构建一套面向多智能体协作的低开销通信、非文本状态传递与共享记忆复用原型系统。

本文档重点回答以下问题：

1. 系统由哪些模块组成。
2. 多智能体如何协作。
3. 结构化通信、非文本状态传递、共享记忆分别如何落地。
4. 当前系统已经实现了哪些能力。

## 2. 赛题目标映射

本系统围绕以下三条主线展开：

1. 低开销通信：在 `baseline_text` 之外，额外实现 `protocol_api` 与 `protocol_api_embedding`，用结构化协议包替代纯自然语言长文本通信。
2. 非文本状态传递：实现 `state_ref / latent_state_ref / hidden_state_ref` 三类中间状态引用机制，支持 embedding 与 hidden state 的直接交换。
3. 共享记忆复用：实现 evidence memory 与 experience memory 两层共享记忆，使后续任务可以检索并复用先前任务中沉淀的事实、证据和经验。

## 3. 总体架构

系统总体由以下部分组成：

1. 多 Agent 运行时
2. 协议解析与调度模块
3. 状态交换模块
4. 共享记忆存储与检索模块
5. 评测与结果导出模块
6. 前端可视化与实验控制模块

整体流程为：

```text
Task Input
-> PlannerAgent
-> RetrieverAgent
-> ReasonerAgent
-> SummarizerAgent
-> Memory Write / Result Export
```

当任务属于 CodeAct 场景时，还会进入：

```text
ReasonerAgent
-> ExecutorAgent
-> SummarizerAgent
```

## 4. Agent 角色分工

### 4.1 PlannerAgent

职责：

- 将任务拆解为有限步骤
- 给 Retriever 提供检索焦点
- 在 protocol / hidden 模式下产出可传递的计划状态引用

输出重点：

- `plan`
- `planner_focus`
- `state_ref / latent_state_ref / hidden_state_ref`

### 4.2 RetrieverAgent

职责：

- 根据问题、计划和共享记忆进行检索
- 区分 evidence memory 与 experience memory
- 把事实证据与经验规则分别传给 Reasoner

输出重点：

- `retrieval_query`
- `context_hits / memory_hits`
- `experience_hits`
- `experience_rules`

### 4.3 ReasonerAgent

职责：

- 基于计划、证据、共享记忆与经验规则形成候选答案
- 在 CodeAct 场景下生成执行请求
- 在部分场景下根据题型做答案收口和后处理

输出重点：

- `answer_candidate`
- `reasoning_summary`
- `limitations`
- `execution_request`（如适用）

### 4.4 ExecutorAgent

职责：

- 仅在 CodeAct 场景执行受限 Python 代码
- 经过 AST 安全检查和轻量隔离后返回结构化执行结果

输出重点：

- `stdout / stderr / result`
- `sandbox_status`
- `execution_metrics`

### 4.5 SummarizerAgent

职责：

- 生成最终答案
- 写入 evidence memory
- 调用 memory refine 逻辑提炼 experience memory
- 输出前端展示所需的写回结果

输出重点：

- `final_answer`
- `latest_evidence_write`
- `latest_experience_write`
- `memory_refine_debug`

## 5. 通信机制设计

系统支持两种通信方式：

### 5.1 纯文本协作模式

对应模式：

- `baseline_text`

特点：

- Agent 间主要通过自然语言文本交互
- 通信成本高，但实现简单，适合作为对照基线

### 5.2 结构化协议协作模式

对应模式：

- `protocol_api`
- `protocol_api_embedding`

特点：

- 使用动作类型、参数、结果、能力需求、状态引用等字段构成高密度协议包
- 降低文本通信开销
- 减少“内部状态 -> 文本 -> 内部状态”的重复转换

协议核心字段包括：

- `action`
- `params`
- `result`
- `state_refs`
- `memory_refs`
- `capability_required`
- `cognitive_gap`
- `confidence`

## 6. 非文本状态传递设计

### 6.1 API embedding 路径

对应模式：

- `protocol_api_embedding`

做法：

- 将 plan / evidence / answer 等中间状态编码为 embedding
- 生成 `latent_state_ref`
- Agent 间只传引用及少量结构化元数据

### 6.2 hidden state 路径

对应模式：

- `latent_hidden`

做法：

- 使用本地模型生成计划与答案
- 提取 hidden state 或 pooled hidden 表征
- 生成 `hidden_state_ref`
- 后续 Agent 通过引用与摘要消费该非文本状态

## 7. 共享记忆设计

当前共享记忆分为两层：

### 7.1 evidence memory

用途：

- 保存摘要、事实、支持证据、执行结果等可直接复用的信息

关键字段：

- `memory_id`
- `source_agent`
- `created_at`
- `task_topic`
- `summary`
- `tags`

### 7.2 experience memory

用途：

- 保存可迁移的策略、避错规则和复用经验

关键字段：

- `problem_pattern`
- `solution_pattern`
- `failure_pattern`
- `trigger_conditions`
- `supporting_evidence`
- `reuse_count`
- `reuse_success_count`
- `experience_source`
- `abstraction_note`

## 8. 当前已实现能力

截至当前版本，已经实现：

1. 不少于 3 个 Agent 的协作闭环
2. 纯文本与结构化协议双模式
3. embedding 与 hidden state 两类非文本状态传递
4. evidence memory 与 experience memory 双层共享记忆
5. 连续任务上的跨轮记忆复用
6. CodeAct 受限执行链路
7. 前端结果展示与 `run_result_json` 导出

## 9. 当前仍待收口的问题

当前主要剩余问题集中在：

1. experience memory 的质量稳定性仍可继续优化
2. hidden 与 protocol 两条路径的部分统计口径仍需统一说明
3. 最终正式实验数据仍需在 openEuler 环境下重跑确认
